## What we know statically

```json
"peerDependencies": {
  "@thatopen/components": "~3.4.6",
  "@thatopen/components-front": "~3.4.3",
  "@thatopen/fragments": "~3.4.6",
  "react": ">=18.2.0",

  "three": "^0.182.0"

"peerDependenciesMeta": {
  "three": { "optional": true },

  "@thatopen/components": { "optional": true },
  "@thatopen/components-front": { "optional": true },

```

**Heavy peers, all marked optional:** `three`, `@thatopen/components`, `@thatopen/components-front`, `@thatopen/fragments` (the 3D/BIM viewer stack). A consumer that doesn't import the 3D-viewer components (`fragment-viewer`, `pages/core-blueprint-viewer*`, `pages/core-building-viewer*`, etc.) should not need to install these — but this is inferred from the peer/optional-peer declaration and the per-component `exports` subpaths (below), not proven by an actual build, since no install was possible.

**Not marked optional but present as regular (non-peer) `dependencies`, and non-trivial in size:** `mapbox-gl`, `echarts`/`echarts-for-react`, the `@tiptap/*` rich-text stack, `@xyflow/react`, `@rjsf/*` (JSON-schema forms), `@tanstack/react-table`. These are always pulled into `node_modules` on install regardless of which components are used; whether they end up in a consumer's *bundle* depends entirely on whether tree-shaking + the per-component `exports` subpaths keep unused component modules (and therefore these deps) out of the graph — see "exports" below. This could not be verified with a real build.

### Exports (`packages/components/src/index.ts` and `package.json#exports`)

`src/index.ts` is **not** a component barrel — it only re-exports types:

```ts
// @wakecap/core-ui - Component library
export * from "./types";
export * from "./types/chat";
```

Every component is its own `package.json#exports` subpath instead — there are **269 export subpaths**, including `./button`, `./badge`, `./card`, `./command`, `./dialog`, `./dropdown-menu`, `./tabs`, `./tooltip`, `./table`, `./sheet`, `./separator`, `./scroll-area`, `./toggle`, `./checkbox`, `./switch`, `./popover`, `./skeleton`, `./progress`, `./select`, `./input`, plus `./styles.css`, `./styles.tw4.css`, and many composed widgets/pages (`./pages/core-*`, `./navigation/*`, `./chat/*`). A consumer imports per-component, e.g. `import { Button } from "@wakecap/core-ui/button"`, never from the package root — this is what makes the "only pull in what you use" tree-shaking story plausible without a bundler even having to work hard at it (each subpath is presumably its own compiled chunk under `dist/`, built by `tsdown`; `dist/` does not exist in the local checkout since it isn't built/published from here).

Spot-checked actual named exports for the four components the brief asks about:
- `button.tsx` → `export { Button, buttonVariants }`
- `badge.tsx` → `export { Badge, badgeVariants }`
- `card.tsx` → `export { Card, CardHeader, CardFooter, CardTitle, CardDescription, CardContent, cardVariants }`
- `command.tsx` → `export { Command, CommandDialog, CommandInput, CommandList, CommandEmpty, CommandGroup, CommandItem, CommandShortcut, CommandSeparator }` — built on `cmdk`, wraps `Dialog`/`DialogContent` from `./dialog`.

### CSS / tokens

`packages/components/package.json#exports` declares two stylesheet subpaths that ship as build output (not present locally since `dist/` isn't built here): `./styles.css` (Tailwind v3 build) and `./styles.tw4.css` (Tailwind v4 build). Components use Tailwind utility classes with a hardcoded **`wwc:` prefix** (e.g. `wwc:flex wwc:h-full wwc:w-full`), so they don't collide with a consuming app's own unprefixed/differently-prefixed Tailwind classes.

`@wakecap/core-tokens` (`packages/tokens/package.json`) ships plain static CSS (its "build" step is literally `cp src/*.css dist/`): `./css` → `dist/index.css`, `./theme` → `dist/theme.css`, `./fonts` → `dist/fonts.css` + font files, and `./tailwind3-preset` → a CJS Tailwind v3 preset (`dist/tailwind3-preset.cjs`). So: **yes, built CSS/tokens ship** — as static files inside each published package, not generated by the consumer.

### The Wakecore repo already has the answer key: `playground/tw3` and `playground/tw4`

`playground/tw4/` (Tailwind v4, the path relevant to this repo since `apps/web` already uses Tailwind v4 + `@tailwindcss/vite`):

```ts
// vite.config.ts
import tailwindcss from "@tailwindcss/vite";
import react from "@vitejs/plugin-react";
export default defineConfig({
  plugins: [tailwindcss(), react()],
  // Consumer declares React 18 but the workspace hoists React 19 (Radix deps resolve
  // their own copy) → duplicate React crashes every asChild/Slot component with
  // "Objects are not valid as a React child". Dedupe forces a single copy.
  resolve: { dedupe: ["react", "react-dom"] },
});
```
```css
/* src/index.css */
@import "tailwindcss" prefix(app);
@import "@wakecap/core-tokens/theme";
```
```tsx
// src/main.tsx
import "@wakecap/core-ui/styles.tw4.css";
```
```tsx
// src/App.tsx
import { Button } from "@wakecap/core-ui/button";
import { Card } from "@wakecap/core-ui/card";
import { Badge } from "@wakecap/core-ui/badge";
// consumer's own utilities use the "app:" prefix, library's use "wwc:" — no collision
```

`playground/tw3/` shows the Tailwind v3 alternative: a `tailwind.config.cjs` with `presets: [require("@wakecap/core-tokens/tailwind3-preset")]` and plain `@tailwind base/components/utilities` — no prefix scheme needed there since v3's `presets` mechanism handles it differently.

**What a standalone Vite app needs, concretely** (from the tw4 playground, cross-checked against `apps/web`'s existing Tailwind v4 + `@tailwindcss/vite` setup):
1. `@wakecap/core-ui` + `@wakecap/core-tokens` installed (blocked, see below) at compatible versions — the playground pins are stale examples (`^0.0.2`/`^0.1.0`), the brief's target is `^0.17.0`/`^0.8.0`.
2. `@tailwindcss/vite` + `tailwindcss` v4 devDeps and the plugin wired into `vite.config.ts` (already true for `apps/web`).
3. `resolve.dedupe: ["react", "react-dom"]` in `vite.config.ts` if React is hoisted/duplicated anywhere in the tree — worth keeping defensively even though `apps/web` pins React 19 itself (peer range `>=18.2.0` is satisfied either way).
4. A CSS entry importing, in order: Tailwind itself (with a project-chosen prefix, e.g. `prefix(app)`, to avoid clashing with the library's `wwc:`-prefixed utility classes), `@wakecap/core-tokens/theme`, and `@wakecap/core-ui/styles.tw4.css`.
5. Per-component subpath imports, e.g. `@wakecap/core-ui/button`, never a root-package import.
