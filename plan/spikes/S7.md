# S7 — Quota and limit data source

Date: 2026-09-18 · Claude Code version: 2.1.275 (Claude Code)

## Method

Step 1 checked whether an official source of 5-hour/weekly usage limits exists (brief's checks a/b/c). Step 2 built and ran the fallback "ccusage method" estimator (`spikes/s7-quota/estimate.ts`) over the real `~/.claude/projects/**/*.jsonl` data (read-only), and compared it against the official numbers observed in step 1.

## Step 1 — official source

### (a) Does the statusline stdin JSON include rate-limit fields?

**Yes, confirmed empirically.** A scratch settings file was used — never the user's real `~/.claude/settings.json`:

```json
{"statusLine":{"type":"command","command":"cat > /tmp/s7-statusline.json; echo s7"}}
```

Launched as `claude --settings /tmp/s7-settings.json` (a disposable session in `/private/tmp`, not one of the user's real projects), sent one prompt ("say hi in 3 words"), then exited with Ctrl-C. `/tmp/s7-statusline.json` (deleted after the probe) contained, among other fields:

```json
"rate_limits": {
  "five_hour": { "used_percentage": 53, "resets_at": 1789752600 },
  "seven_day": { "used_percentage": 84, "resets_at": 1789916400 }
}
```

`resets_at` is Unix epoch seconds. The interactive banner printed in the same session independently read **"You've used 84% of your weekly limit · resets Sep 20 at 6pm (Asia/Riyadh)"**, which matches `seven_day.used_percentage: 84` and `resets_at: 1789916400` (2026-09-20 18:00 local) exactly — cross-confirming the field is live, correct data, not a stale/placeholder value.

No user session, real settings file, or transcript was touched: the probe ran in `/private/tmp` under a scratch settings file, and the scratch session/statusline files were deleted afterward.

### (b) Does `claude /usage` or `/status` show 5h/weekly limits?

**Not checked by me — left for the user, as instructed.** Interactive slash commands require a live TTY session with visual confirmation (a screenshot), which is outside what I can safely automate here (the brief and this task's safety rules both call for the user to do this by hand). The statusline banner text observed in (a) ("You've used 84% of your weekly limit...") strongly implies `/status`/`/usage` shows the same `rate_limits.seven_day`/`five_hour` figures, but the user should confirm by running `/status` (or `/usage`) interactively and comparing the percentages/reset times to the numbers above.

### (c) Is there a documented source?

`claude --help` lists no `usage`, `status`, `quota`, or `limit` subcommand or flag — nothing outside an interactive session.

Consulted the official docs via the claude-code-guide agent (`https://code.claude.com/docs/en/statusline.md`): the **statusLine feature is the documented, official channel**. The "Available data" / "Full JSON schema" section documents:

- `rate_limits.five_hour.used_percentage` (0–100), `rate_limits.five_hour.resets_at` (Unix epoch seconds)
- `rate_limits.seven_day.used_percentage` (0–100), `rate_limits.seven_day.resets_at` (Unix epoch seconds)
- `rate_limits.spend_limit.used_percentage` / `.resets_at` (Claude apps gateway only)

The docs' own "Rate limit usage" example script reads these same fields. Caveats documented there: rate limits only appear for Pro/Max subscribers (or behind the Claude apps gateway), and only *after* the session's first API response (matches what was observed: the field was present only once a message had actually round-tripped). No CLI flag, env var, or separate API endpoint exists — statusLine is the sole official channel. No mention of ccusage or any community tool as an officially sanctioned alternative.

## Step 2 — fallback estimator ("ccusage method")

`spikes/s7-quota/estimate.ts` (as specified in the brief, unmodified) run with `pnpm exec tsx spikes/s7-quota/estimate.ts` over the real `~/.claude/projects` tree (read-only), immediately after the statusline probe in step 1:

```
{
  weekTokens: 83611273,
  blocks: 26,
  current: {
    start: '2026-09-18T12:00:00.000Z',
    resetsInMin: 190,
    tokens: 4387555,
    msgs: 651
  }
}
```

### Estimator vs. official, side by side

| metric | official (`rate_limits`) | estimator |
|---|---|---|
| current 5h window resets | 2026-09-18 20:30 local (`five_hour.resets_at`), ~220 min out at probe time | 190 min out (measured ~4 min later, after the probe's own session added tokens to the current block — consistent with the drift) |
| current 5h usage | 53% of quota | 4,387,555 tokens, 651 msgs (no percentage — denominator unknown) |
| weekly usage | 84% of quota (`seven_day.used_percentage`) | 83,611,273 tokens across 26 five-hour blocks in the trailing 7 days (no percentage) |

The estimator's block-boundary heuristic (floor timestamp to the hour, 5h window) landed close to the real reset time, but it cannot produce a percentage at all — it has no way to know the account's actual token/message quota ceiling, only raw token counts from transcripts. It is also blind to any requests that didn't produce a local transcript line (e.g. a session on another machine, or Claude Code invoked via the API/SDK with local logging disabled), so `weekTokens` is a floor on real usage, not an exact figure.

## Decision

**official.** Field path: the `statusLine` command's stdin JSON payload —

- `rate_limits.five_hour.used_percentage`, `rate_limits.five_hour.resets_at`
- `rate_limits.seven_day.used_percentage`, `rate_limits.seven_day.resets_at`

This is Anthropic's own accounting (matches the interactive UI banner exactly), gives true percentages against the real quota (something the estimator structurally cannot do), and is documented/stable API surface, not a reverse-engineered heuristic.

**Integration plan for Phase 1:** orchestrator should not compete with the user's own `statusLine` — instead, merge into it (or install a wrapper `statusLine` command that both renders the user's existing statusline and tees the JSON to a file/socket the daemon tails), so the registry gets a live `rate_limits` update on every turn without polling. Reserve the `spikes/s7-quota/estimate.ts` estimator as a fallback for: (1) accounts on plans where `rate_limits` doesn't appear (non-Pro/Max), (2) historical/weekly trend charts that need per-session/per-project breakdown the statusline snapshot doesn't carry, and (3) any UI that shows this fallback data must label it **"estimated"** — it is not Anthropic's own number and both the block-boundary heuristic and the missing-transcript blind spot mean it will not exactly match `rate_limits`.

## What the user still needs to confirm interactively

1. Run `/status` (or `/usage`) in a normal interactive session and check the percentages/reset times shown match a concurrently-captured `rate_limits` statusline reading (this spike could not drive that interactive command itself — see (b) above).
2. Confirm whether `rate_limits` is present on every plan tier the target users are on, or only Pro/Max/gateway as the docs state — if some users are on a tier without it, the daemon needs the estimator as the only source for them, not just a fallback.
3. Decide whether it's acceptable for orchestrator to modify/wrap the user's `statusLine` setting to capture this data continuously, versus prompting the user to add a small tee manually — this spike did not modify the user's real `~/.claude/settings.json` and any such change in Phase 1 needs explicit design/consent.

## Safety notes

- The statusline probe used only a scratch settings file (`/tmp/s7-settings.json`) and a disposable session under `/private/tmp`; the user's real `~/.claude/settings.json` was never read or written.
- No `/usage` or `/status` command was run interactively by me, and no running user `claude` session was started, stopped, or sent input.
- The estimator only ever aggregates token counts and message counts per model/time-block; no prompt text, transcript content, or tokens (in the literal-text sense) are printed or retained — only the aggregate numbers shown above.
