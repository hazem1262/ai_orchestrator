## Open question: `tool_result` classification (toolUseResult vs sourceToolAssistantUUID)

`docs/04-data-sources.md` defines a tool-result record as having **both** `toolUseResult` and `sourceToolAssistantUUID`. `packages/core/src/claude/records.ts` currently classifies a `user`-type record as `tool_result` if it has `toolUseResult !== undefined` **or** a `tool_result` content block — it never inspects `sourceToolAssistantUUID`.

Measured over the real data (210,285 lines):

| condition | count |
|---|---|
| records with `toolUseResult` present | 42,408 |
| records with `sourceToolAssistantUUID` present | 43,216 |
| records with both | 42,408 |
| records with `toolUseResult` but no `sourceToolAssistantUUID` | 0 |
| records with `sourceToolAssistantUUID` but no `toolUseResult` | 808 |

Every record that has `toolUseResult` also has `sourceToolAssistantUUID` — so the docs' AND condition would never disqualify anything the current classifier accepts via the `toolUseResult` branch. The 808 records that have `sourceToolAssistantUUID` but no `toolUseResult` were checked separately: all 808 are `type: "user"` records whose `message.content` contains a `tool_result` content block, so the current classifier's second branch (`hasToolResultBlock`) already classifies every one of them as `tool_result`. Net result: the current OR-based classifier (`toolUseResult` present OR a `tool_result` content block) already captures the full set that the docs' AND definition would, plus it is robust to the 808 cases where `sourceToolAssistantUUID` is present without `toolUseResult`.

**Recommendation:** do not change `records.ts`. Its existing logic is strictly correct (no under- or over-classification found) and more robust than the docs' definition. `docs/04-data-sources.md` should be corrected instead, to describe a tool-result record as one with `toolUseResult` **or** a `tool_result` content block, since `sourceToolAssistantUUID` was observed to be neither necessary nor sufficient on its own in the real data. This task does not change either the code or the docs — filing that doc correction is left to a follow-up.
