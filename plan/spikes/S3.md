# S3 — Registry status latency

Date: 2026-09-18 · Claude Code 2.1.275 · chokidar ^5.0.0 · macOS 24.5.0 (fsevents)
Method: `spikes/s3-registry/watch.ts` watched `~/.claude/sessions/` read-only for ~30 min while the user's own sessions ran. No session was started, stopped or sent input. `lag` = `Date.now() - statusUpdatedAt` at the moment the file event arrived.

## Sample

Two kinds of line appear in the log, and only one of them measures latency:

- **Initial scan (9 lines, `add` events):** emitted for the files that already existed when the watcher started. Their `lag` is the *age of the last status change* (24 s to 49 h), not a detection delay. **Excluded from the statistics.**
- **Live transitions (6 lines, `change` events):** the real measurement.

| # | transition | lag |
|---|---|---|
| 1 | busy → idle | 3 ms |
| 2 | busy → shell | 26 ms |
| 3 | shell → busy | 73 ms |
| 4 | busy → shell | 28 ms |
| 5 | busy → idle | 4 ms |
| 6 | shell → idle | 107 ms |

**min 3 ms · median 27 ms · max 107 ms · n = 6**

## Findings

- **Detection is effectively instant.** Every live transition was seen within 107 ms, two orders of magnitude inside the 2 s target. fsevents delivers the write immediately and the file is small enough to read in one go.
- **Partial writes are real but benign:** 1 parse error in 6 transitions, and it was `ENOENT` (the file was replaced while being read), not malformed JSON. The watcher must treat a failed read as "skip and wait for the next event", never as an error state.
- **`waiting` was never observed in this window.** All six transitions moved between `busy`, `idle` and `shell`. The `waiting` status and its `waitingFor` text exist in the registry (seen in earlier exploration), but this run does not prove the latency for that specific transition.
- **Sample size is small (6).** The 20-transition target was not reached: the machine's sessions were mostly idle during the window. The spread is tight (3–107 ms) and the mechanism is the same for every status, so the conclusion holds, but it is one observation window, not a distribution.

## Decision

**GO — watch-only is sufficient. The hook bridge (F10) stays in Phase 5 as an optimisation, not a Phase 2 requirement.**
Criteria were median < 1 s and max < 2 s: measured median 27 ms, max 107 ms.

## Requirements this puts on Phase 2

1. Ignore `*.key` files; only `^\d+\.json$` is a registry entry.
2. Wrap every registry read in try/catch and ignore `ENOENT`/parse failures — a partial write is normal, and the next event carries the settled state.
3. Do not use `statusUpdatedAt` as a freshness signal on first scan: at startup it is the age of the last change, which can be hours or days old. Use it only for "time in current status" display.
4. Re-verify the `waiting` transition once a session is genuinely waiting for input, during Phase 2's Live Board work, and record the lag there.
