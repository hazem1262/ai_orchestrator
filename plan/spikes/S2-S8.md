### A real bug found and fixed along the way

`node-pty@1.1.0`'s prebuilt `prebuilds/darwin-arm64/spawn-helper` binary ships **without the executable bit** in this npm install (`-rw-r--r--`), which makes every `pty.spawn(...)` fail immediately with `Error: posix_spawnp failed.` — reproduced first with `/bin/echo`, not just `claude`. Fixed locally with `chmod +x node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper`. This is worth carrying into Phase 1: either add a `postinstall` chmod step for the daemon's own `node-pty` dependency, or verify whether this is fixed in a newer `node-pty` patch release before Phase 1 ships.

### Check (e) detail — 50/50

Method: a persistent WS client accumulated the raw PTY byte stream; for each `i` in 0..49 it sent `{"t":"say","text":"reply with the single word ok "+i}`, waited for the stream to go idle (no new bytes for 1.2 s, capped at 20 s), ANSI-stripped the bytes that arrived since the send, and checked for `\bok\s+i\b`. A 0.8 s settle gap separated iterations (idle-detected, not a fixed 4 s sleep — see "Decisions" below). All 50 iterations matched on the first check, and the matched indices were strictly increasing (no reordering).

### Check (f) — send while busy: **queued cleanly**

Sent `say('write the numbers 1 to 40, one per line, and nothing else')`, then — 600 ms later, well before that turn could finish — sent `say('reply with the single word zulu')`. Raw (ANSI-stripped) transcript segment shows, in order:
1. The first prompt echoed and processed (`Newspapering…` status).
2. The second `sendText()` call (bracketed paste + `\r`) landed **while busy**. Claude Code's own TUI intercepted it as a **queued** message: the transcript shows the literal UI text `ctrl+x ctrl+s to send now` and `Press up to edit queued messages · esc to interrupt` — this is the CLI's own input-queue affordance, not something the spike built.
3. The first turn completed with the numbers 1-40 intact and in order (visible as sequential number fragments in the stripped output, broken across redraw frames but not out of order or corrupted).
4. The queued second turn then ran automatically (`Waddling…` status) and produced a single, correct `zulu` reply.

No interleaving/corruption of the first task's output was observed, and `zulu` was not typed mid-stream into the first response. **Conclusion: Claude Code's TUI already queues input submitted via `\r` while busy; `sendText()` does not need to gate on idle status before writing — worst case, the write is queued by the CLI itself.**

### Check (g) — multi-line paste: **one prompt, one turn**

Sent `say('reply with the single word alpha\nreply with the single word beta')`. Raw transcript shows the submitted prompt echoed as **two visually separate lines inside one prompt box** (`❯ reply with the single word alpha` / `reply with the single word beta`, no assistant response between them), followed by exactly one `Improvising…` processing indicator and one assistant turn that replied with `alpha beta` in a single response (`⏺ alpha beta`). The embedded `\n` stayed inside the bracketed-paste region and was not treated as an Enter keystroke — no split into two separate submitted turns was observed.

## Decisions for Phase 1

- **`submitDelayMs`:** the module's default (120 ms) was used unmodified for all 52 scripted sends (50 for check e, 1 each for f and g) and every one produced a correctly-submitted, complete turn. No failures or partial submissions were observed at 120 ms. **Keep 120 ms as the default; no evidence it needs raising.**
- **Need idle detection before send?** **No, not for correctness** — check (f) shows Claude Code's own TUI queues a second submission received while busy rather than corrupting the in-flight turn. Phase 1 can send without checking registry status first and rely on the CLI's queuing. That said, idle detection is still worth doing for **UX** (so the orchestrator's own queue indicator matches what actually happened, and so a caller isn't surprised that a "send" was silently deferred) — this is a product decision, not a correctness requirement uncovered by this spike.
- **Bun PTY evaluated?** Not evaluated — out of scope for this task and no time pressure to do so; Node (`node-pty`) stays default per the brief.
- **node-pty packaging bug:** `prebuilds/darwin-arm64/spawn-helper` ships without the executable bit in `node-pty@1.1.0` as installed here; every `pty.spawn()` fails with `posix_spawnp failed` until `chmod +x` is applied. Phase 1 must handle this (postinstall chmod, or confirm a newer patch fixes it) or every daemon PTY spawn will fail on a fresh macOS arm64 install.
- **Claude Code self-update mid-session:** the CLI auto-updated itself (2.1.275 → 2.1.276) inside the long-running resumed PTY session during the check-f run (visible in the raw transcript as "✔ Update installed · Restart to update"). This did not interrupt the PTY or break subsequent scripted sends (check (g) ran immediately after with clean results), but Phase 1 should know that a resumed session's underlying binary version can change under it without the process restarting.

### CRITICAL finding for Phase 1 — child-session env inheritance

The resumed session's own status line reads:

> `Transcript saving is off - inherited CLAUDE_CODE_CHILD_SESSION marker - restart with CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1 to keep future transcripts`

The harness inherited `CLAUDE_CODE_CHILD_SESSION` from the Claude session that spawned it, and **a session launched that way writes no transcript**. An orchestrator daemon started from inside a Claude session would inherit the same marker, so every session it launched or resumed would be invisible to the indexer — the app's core promise, silently broken.

**Phase 1 requirement:** `PtyManager.spawn()` must sanitise the environment it passes to a child - delete `CLAUDE_CODE_CHILD_SESSION` (and any sibling `CLAUDE_CODE_*` marker that signals a nested session) and set `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1`. Add a test that asserts the spawn env contains neither marker, and a startup check that warns if the daemon's own env carries one.
