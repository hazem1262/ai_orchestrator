## Live process → rollout matching

One live `codex` process was running during the probe:

- `pid 85369` — `node /Users/hazem/.npm-global/bin/codex` (wrapper)
- `pid 85370` — the actual `@openai/codex-darwin-arm64` binary (child of 85369)
- `lsof -a -p <pid> -d cwd -Fn` resolved cwd for both to `/Users/hazem/Wakecap` — this part of the matching rule works cleanly and requires no special privileges beyond what `lsof` already allows for the invoking user.

**Matching rule (as specified in the brief):** match a live process to its rollout by (1) resolving the process's `cwd` via `lsof -a -p <pid> -d cwd -Fn`, then (2) scanning `~/.codex/sessions/**/*.jsonl` for the rollout file whose `session_meta` recorded that same `cwd` and whose file mtime is newest and under 10 s old (i.e., a write happened essentially "now").

**Result: partially validated, not fully.** At probe time the live process's cwd resolved correctly (step 1 confirmed), but the newest rollout file on disk anywhere under `~/.codex/sessions` was ~26.3 hours old (`rollout-2026-09-17T14-10-51-*.jsonl`, mtime 2026-09-17T11:12:43Z vs. probe time 2026-09-18T13:33Z) — no file had been touched in the preceding 10 minutes, let alone 10 s. This means the running process was idle (no in-flight turn) at probe time, so step 2 of the rule (mtime < 10 s) could not be exercised against a real write. The mtime component of the rule is therefore **untested under load**; it is expected to work because Codex appends to the rollout file synchronously per turn event, but that was not observed directly here. If a future run catches a process mid-turn, re-run the probe and confirm the newest rollout's mtime is fresh and its cwd matches the process's `lsof` cwd.

## `state_5.sqlite` — thread names and status

Tables: `_sqlx_migrations`, `threads`, `sqlite_sequence`, `thread_dynamic_tools`, `backfill_state`, `thread_spawn_edges`, `remote_control_enrollments`, `external_agent_config_imports`, `thread_sections`, `rollout_migration_state`, `rollout_migration_skipped_rollouts`, `projects`, `project_roots`, `project_idempotency_keys`, `thread_attachments`.

- `threads` **does** hold thread names: columns `name`, `title`, `preview`, plus `cwd`, `project_id`, `rollout_path`, `created_at`/`updated_at` (and `_ms` variants), `archived`/`archived_at`, `model`, `reasoning_effort`, `originator`, `git_sha`/`git_branch`/`git_origin_url`, `tokens_used`, `has_user_event`, `recency_at`/`recency_at_ms`.
- `threads` does **not** have a dedicated per-turn `status` column; the closest is `archived` (a coarse lifecycle flag) and `has_user_event`.
- Turn-level **status** lives in the companion DB, `thread_history_1.sqlite`, table `thread_turns`, column `status` (alongside `error_json`, `started_at`, `completed_at`, `duration_ms`, `rollout_byte_offset`/`rollout_end_byte_offset`, `rollout_ordinal`/`rollout_end_ordinal`).
- `thread_history_1.sqlite` also has `thread_items` (`item_json`, `item_type`, `rollout_ordinal`) and `thread_realtime_items`, which look like a live/streaming mirror of items as they're appended — this is a promising direct source for "what is this thread doing right now" instead of tailing the rollout file.

Only table and column names were read; no row contents were queried or printed, consistent with the read-only/no-row-content constraint.

## Decision: rollout-only vs. also reading SQLite

**Also read SQLite (read-only), do not rely on rollout files alone.**

Reasons:
1. `state_5.sqlite.threads` gives a direct `cwd` → `thread` → `rollout_path` mapping without needing to walk and mtime-sort the whole `~/.codex/sessions` tree — this is cheaper and less racy than the filesystem-scan half of the matching rule described above.
2. `thread_history_1.sqlite.thread_turns.status` gives an authoritative per-turn status (started/completed/error) that the rollout JSONL does not expose as a single field — it would have to be reconstructed by replaying `event_msg:task_started` / `task_complete` / `turn_aborted` records.
3. `thread_realtime_items` looks purpose-built for "live" consumption, which is closer to what a registry/status watcher needs than tailing a growing `.jsonl` file.
4. Caveat: `rollout_migration_state` / `rollout_migration_skipped_rollouts` tables imply the SQLite state can lag behind or diverge from the raw rollout files during a migration — any consumer should treat SQLite as the primary source for status but keep the rollout file as the fallback/ground truth, and should always open the DB with `{ readonly: true, fileMustExist: true }` and re-open per read (no persistent write handle) to avoid interfering with Codex's own WAL writers.

## Safety notes

- SQLite files were opened strictly read-only; only `sqlite_master` and `pragma table_info(...)` were queried. No row contents were printed or retained.
